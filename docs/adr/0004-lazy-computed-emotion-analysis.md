# 情绪分析采用懒计算+缓存触发

情绪分析需要调用 LLM（耗时 2~6 秒、按次计费），而 GET /session/{id}/emotion 在前端有三处触发（AI 回复 done、流关闭、点击会话）。决定采用懒计算+缓存：GET 时比较会话最新消息的 `created_at` 与 `last_emotion_updated_at`，缓存新鲜则直接返回库中 JSON 快照（零 LLM 调用）；有新消息或从未分析才同步执行 LLM 分析、写库后返回。`last_emotion_updated_at` 的语义由"情绪端点被读取时"更正为"分析完成于"——原 GET 中的 `touchEmotionUpdatedAt()` 调用因此移除。

## Considered Options

- 每次实时分析（无缓存）：被否决——点击旧会话重复分析、前端 done+onclose 双触发直接双倍调用、每次等 2~6 秒。
- 后台异步预计算（AI 回复落库后自动分析）：被否决——需要新增后台任务机制，且"前端 done 后立刻 GET、分析尚未完成"的竞态需要额外协调，复杂度不成比例。
- 懒计算+缓存：只有被消费且过期的数据才花钱分析，旧会话秒回，无后台任务。

## Consequences

- 首次分析同步阻塞请求 2~6 秒，前端情绪花园需 loading 态。
- 缓存失效粒度为"任意新消息"：每批新消息最多分析一次（滑动窗口重叠是设计使然，不是重复消费）。
- 并发去重（分析进行中的重复 GET join 同一 Future）成为端点职责，防止切回会话/双开标签页窗口内的重复 LLM 调用。
- 降级策略依赖缓存：分析失败返回旧快照，因此响应需携带 `analyzedAt` 让用户感知时效。
