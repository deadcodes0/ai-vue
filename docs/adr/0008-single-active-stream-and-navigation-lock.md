# 单活跃流与导航锁

前端流式回复的写入目标是"到达时刻 messages 数组的最后一条"（`onmessage` 内按索引回查），而流式期间切换会话会整体替换 `messages`——两者组合导致跨会话串台：A 会话的 AI 分片粘到 B 会话最后一条消息上。根因是流状态没有所有权：写入目标随视图漂移。决定两层修复：写入目标改为流启动时闭包捕获的那条 AI 消息（正确性，无条件做）；并确立**单活跃流**约束（词汇表"活跃回复"）——同一用户同一时刻至多一条活跃回复，其存在期间禁止发送新消息、切换会话、新建会话、删除所属会话（导航锁）。配套修复：`done` 事件的副作用（情绪分析）改绑流所属会话而非当前显示的会话；新建会话时清空消息区（原实现残留上一会话的历史消息，是另一条独立于流式的串台路径）。

## Considered Options

- 自由导航（仅修闭包捕获，不加锁）：被否决——切到 B 后 B 的输入被全局 `isAiTyping` 无故阻塞（"A 的流挡住了 B"），切回 A 时进行中的半截回复从视图消失（尚未落库），体验不一致且难以解释。
- 切走即 abort：被否决——后端 AI 回复只在 `doOnComplete` 落库，客户端 abort 触发 Reactor cancel，回复永久丢失（LLM token 已消耗）。要救需迁移到 `doFinally` 保存部分回复，引入"残句入库"污染对话记忆与情绪分析输入的新问题。
- 多流分区（消息按会话分 store，流只写自己的分区，视图为投影）：被否决——体验最优但需处理"切回时流未完成、DB 尚无该消息"的合并/去重边界，复杂度与"流式期间切换会话"这一低频操作的收益不成比例。

## Consequences

- AI 回复生成期间（可达 10s+）用户不能切换/新建/删除所属会话，体验有损，属有意为之；输入框与会话列表的禁用口径由此统一。
- 路由跳转（组件卸载）时流**不** abort：后台跑完自然落库，这是数据安全的现状。后端 `streamPsychologicalChat` 已留注释警告——勿"优化"成 unmount-abort，那会把体验优化变成数据丢失。
- 双开标签页对同一会话并发发起流式无后端守卫（两条用户消息与两条 AI 回复交错落库），记录为已知限制；如需防护可复用情绪分析已验证的 in-flight 去重模式（ADR 0004）。
- 未来若产品要求"切走不等待"，升级路径是先做后端 `doFinally` 部分落库，再做前端多流分区，两者都有明确的边界但需独立立项。
