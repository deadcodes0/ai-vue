- **AI 流式对话与断线重连：**基于 **Reactor Sinks 可回放热流**解耦模型生成与订阅，经 **SSE** 推送至前端，支持刷新/切页后重连**续看**而不重复触发 LLM 调用。

# 功能上的必要性
> 冷流数据只能在订阅时生成，不能回放。
> 热流数据可以在订阅时回放，也可以在订阅后回放。
> 所以，必须有热流来缓存和广播数据。

# 解耦：有两条订阅链。
一条是 内部订阅者 → LLM 冷流（链 A），负责生产数据。内部订阅者主动订阅 LLM，把 LLM 推来的 chunk 写入 Sinks。
另一条是 SSE 订阅者 → Sinks 热流（链 B），负责接收数据。SSE 订阅者订阅 handle.asFlux()，从 Sinks 接收数据并推给浏览器，通过背压请求额度控制节奏。
两条链的订阅生命周期互相独立。它们通过 Sinks 桥接：Sinks 不订阅 LLM，是链 A 订阅 LLM 后把数据写进 Sinks；Sinks 只负责被动接收、缓存和广播。
浏览器断开只取消链 B（对热流的订阅），不终止热流本身，也碰不到链 A，所以 LLM 继续跑完。
真正能终止链 A 的只有：
显式停止/删除会话（通过 handle 里的 Disposable 手动取消）；
LLM 自然完成（onComplete 触发收尾）；
超时（take(Duration) 触发 onComplete 收尾）。
自然完成和超时都会走 onComplete 回调，完成落库、释放槽位、终止 Sinks。

# 为什么不能省掉订阅
```java
replyChain.subscribe(...);
```
因为 chatClient.prompt()...stream().content() 返回的是冷流。冷流的定义就是：
不订阅，不执行。


# 为什么不由 SSE handler 来触发这个订阅？

有人会想：那我在 SSE handler 里写不就行了？

```java
@GetMapping("/chat/stream")
public Flux<String> stream(...) {
    Sinks.Many<String> llmHot = Sinks.many().replay().all();
    chatClient.prompt()...stream().content()
        .subscribe(llmHot::tryEmitNext, ...);
    return llmHot.asFlux();
}
```

这确实“LLM 直接接上浏览器”了。但会引入四个问题：

### 问题一：每次 SSE 连接都重新触发一次 LLM

每个浏览器连接进来，都执行一次 `subscribe`，LLM 就重新跑一次。  
刷新页面 → 重新跑；多端观看 → 各自跑一份。这不是共享，是重复生成。

### 问题二：槽位抢占没有挂载点

你的业务要求“同一用户同时只能有一个 AI 回复”。  
槽位抢占必须和“LLM 开始跑”原子发生。放在 SSE handler 里，抢占时机就跟着浏览器走，控制不住。

### 问题三：取消权跑到浏览器手上

如果 LLM 订阅是在 SSE handler 里创建的，那这个订阅的 `Disposable` 就归 SSE handler 管。浏览器断开 → 取消 → LLM 被取消。  
你又回到了“刷新页面就断生成”的老问题。

### 问题四：收尾逻辑没有归属

LLM 跑完后要落库、释放槽位、终止 sink。  
这些逻辑需要一个**独立的生命周期钩子**来挂载。放在 SSE handler 里，每次连接都挂一遍，重复落库、重复释放。

# 为什么槽位抢占推迟到真正订阅那一刻进行？
> 槽位必须和“生成真正启动”绑定，而生成真正启动的时刻就是订阅时刻。
> 如果先抢槽位、再订阅，两者之间就有一个窗口：槽位被占着，但 LLM 还没开始跑。这个窗口里如果订阅没发生、订阅者取消了、或者中间抛异常，槽位就变成幽灵占位——资源被占死，别人进不来，却没有任何生成在进行。
> 所以槽位抢占不能提前，必须推迟到订阅那一刻，和 replyChain.subscribe(...) 原子地发生：要么一起成功（槽位占用 + LLM 启动），要么一起不发生。

> 热流的生命周期
> 谁创建它: ActiveReplyHandle 实例化时创建Sinks热流，而 ActiveReplyHandle 在槽位抢占成功，准备开始AI回复的那一刻创建。
> 谁往里写数据: LLM 冷流把数据写入热流。
> 谁终止它：热流的终止由链 A 的完成/出错回调触发，本质上是 LLM 跑完或出错之后才终止。Sinks.Many 
> 的终止只有两条路：
```java
handle.emitComplete();          // 正常结束
handle.emitError(error);        // 异常结束
```
> 订阅者取消，会影响热流生命周期吗: 不会。
> 这正是选 replay().all() 而不是 multicast() 的原因：ulticast().onBackpressureBuffer() 默认 autoCancel=true：订阅者归零 → sink 自动终止并清缓冲；最重要的原因是迟到订阅者拿不到历史数据。
> replay().all()：订阅者归零 → sink 照常存在，历史保留。

# 热流和冷流的区别
> **冷流内置生产逻辑，订阅即生产；热流没有生产逻辑，只是广播通道，数据必须由外部写入。**
>
> **热流可以“看起来”在产生数据，但真正生产数据的永远是外面那个写入者——可能是手动 emit，可能是链 A 的订阅者，可能是操作系统事件源。热流自己，不会。**
>
> **热流是接入，冷流是启动：冷流的订阅是“启动生产 + 接入观看”，两者绑定；热流的订阅只是“接入观看”，启动生产由外部独立完成。**
> 冷流：你订了，它才跑。        → 订阅 = 启动 + 接入
> 热流：它一直在跑，你订只是看。  → 订阅 = 接入

# 浏览器是 SSE 客户端，不是 Reactor 订阅者。但一条浏览器连接，会在服务端对应一个 Reactor 订阅者。断开时，是服务端去取消那个订阅者，不是浏览器直接调用 cancel()。

# 为什么选 replay().all()
选 `Sinks.many().replay().all()` 不是随手挑的，而是**需求逐条排除后的唯一选择**。我们按“排除法”来看。

## 1. 先把需求列清楚

你这段代码对“热流载体”的要求有 7 条：

| # | 需求 | 来源 |
|---|---|---|
| 1 | 订阅者归零后，流不能自杀 | 断线重连场景 |
| 2 | 迟到/重连订阅者要拿到全量历史 | 重连后补全 |
| 3 | 支持多个订阅者共享同一份数据 | 多端观看 |
| 4 | 写入端和读取端要分离 | 只有链 A 能写，链 B 只能读 |
| 5 | 能被封装成一个可管理对象 | `ActiveReplyHandle` |
| 6 | 支持显式终止（complete/error） | 落库、释放槽位 |
| 7 | 启动动作要能由业务显式控制 | 槽位抢占原子衔接 |

## 2. 逐个排除其他算子

### ❌ `Flux.create()` + 手动多播

老方案，注释里点名的“可重入地雷”：

- 每次订阅都重新执行桥接逻辑 → 重复 LLM 调用 + 重复落库；
- 没有内置回放；
- 手动管理订阅者列表，容易出并发 bug。

**违反需求 1、2、4。**

### ❌ `Sinks.many().multicast().onBackpressureBuffer()`

默认 `autoCancel=true`：

- 订阅者归零 → sink 自动终止并清缓冲 → 重连接不上；
- 即使设 `autoCancel=false`，它的 buffer 也不是回放缓冲，迟到订阅者拿不到历史。

**违反需求 1、2。**

### ❌ `Sinks.many().unicast()`

只允许一个订阅者：

- 多端观看直接崩；
- 重连时旧订阅者还没完全清理，新订阅者就进不来。

**违反需求 3。**

### ❌ `ConnectableFlux + publish().connect()`

`publish()` 是多播但**无回放**：

- 迟到订阅者只能收到订阅之后的数据；
- 重连后断开期间的历史全丢。

**违反需求 2。**

### ❌ `ConnectableFlux + replay().connect()`

这个能满足需求 1、2、3，但：

- `connect()` 只返回一个 Disposable，onNext/onError/onComplete 回调必须预先用 `doOnNext` / `doOnError` / `doOnComplete` 挂在上游；
- 没有一个天然的“业务对象”来持有流状态、Disposable、对外接口；
- 你仍然需要额外写一个类把 `ConnectableFlux + Disposable + 状态` 包起来——**而这个类，本质上就是 `ActiveReplyHandle`，只不过你改用 `Sinks` 来实现它。**

**违反需求 4、5 的便利性。**

### ❌ `share()`

`share()` = `publish().refCount()`：

- 第一个订阅者到来才订阅上游 → 启动时机被浏览器控制；
- 最后一个订阅者离开 → **取消上游** → LLM 被取消；
- 无回放。

**违反需求 1、2、7，还额外引入“断连取消 LLM”。**

### ❌ `cache()`

- 第一个订阅者触发上游订阅 → 启动时机被浏览器控制；
- 取消语义取决于实现，不可靠；
- 没有写入端 API，无法显式 `tryEmitNext`；
- 没有显式终止接口。

**违反需求 4、6、7。**

### ❌ 旧版 `Processor`（`EmitterProcessor` / `ReplayProcessor`）

- Reactor 3.4 起已废弃，被 `Sinks` 取代；
- `ReplayProcessor` 虽然支持回放，但 API 老、语义混乱、没有 `tryEmitNext` 的返回值检查。

**违反“用现代 API”的隐含要求。**

## 3. 为什么是 `replay().all()` 而不是 `replay().limit(n)`

`Sinks.many().replay()` 有三个变体：

| 变体 | 语义 | 是否满足 |
|---|---|---|
| `replay().all()` | 保留全部历史 | ✅ |
| `replay().limit(n)` | 只保留最近 n 条 | ⚠️ 可能丢历史 |
| `replay().limit(Duration)` | 只保留最近一段时间 | ⚠️ 可能丢历史 |

为什么选 `all()`：

- LLM 回复的长度是**有限且可控**的（有 `REPLY_MAX_SECONDS` 超时兜底）；
- 一次生成的生命周期很短，跑完就释放 handle，内存不会长期增长；
- 重连场景要求“断开期间的历史一条都不能少”，`limit(n)` 可能截断开头，导致回放不完整；
- 回复完成后 `emitComplete()`，sink 本身随之可被回收。

所以 `all()` 在你这个“短生命周期 + 要求完整回放”的场景下是安全的。  
如果换成“长期运行的行情推送”，`limit(n)` 或 `limit(Duration)` 才更合适。

## 4. `Sinks.many().replay().all()` 同时满足所有需求

| 需求 | 满足方式 |
|---|---|
| 1. 订阅者归零不自杀 | `replay` 不依赖 `autoCancel`，sink 独立存在 |
| 2. 迟到订阅者拿全量历史 | `all()` 保留全部元素 |
| 3. 多订阅者共享 | `Sinks.Many` 本身是多播 |
| 4. 写入/读取分离 | `tryEmitNext`（写）vs `asFlux()`（读） |
| 5. 可封装成对象 | `Sinks.Many` 作为字段放进 `ActiveReplyHandle` |
| 6. 显式终止 | `tryEmitComplete` / `tryEmitError` |
| 7. 启动由业务控制 | 写入由链 A 的 `subscribe(...)` 驱动，与 sink 解耦 |

## 5. 对比总表

| 方案 | 不自杀 | 回放 | 多播 | 写读分离 | 可封装 | 显式终止 | 启动可控 |
|---|---|---|---|---|---|---|---|
| `Flux.create` | ❌ | ❌ | ⚠️ | ❌ | ⚠️ | ❌ | ⚠️ |
| `multicast().onBackpressureBuffer()` | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ | ✅ |
| `unicast()` | ✅ | ⚠️ | ❌ | ✅ | ✅ | ✅ | ✅ |
| `ConnectableFlux.publish()` | ✅ | ❌ | ✅ | ⚠️ | ⚠️ | ⚠️ | ✅ |
| `ConnectableFlux.replay()` | ✅ | ✅ | ✅ | ⚠️ | ⚠️ | ⚠️ | ✅ |
| `share()` | ❌ | ❌ | ✅ | ⚠️ | ⚠️ | ⚠️ | ❌ |
| `cache()` | ⚠️ | ✅ | ✅ | ❌ | ⚠️ | ❌ | ❌ |
| 旧 `ReplayProcessor` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅（但已废弃） |
| **`Sinks.replay().all()`** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

## 6. 一句话总结

> **`Sinks.many().replay().all()` 是唯一同时满足“不自杀 + 全量回放 + 多播 + 写读分离 + 可封装 + 显式终止 + 启动可控”这七条的现代 API。**
>
> 其他算子要么缺回放（`multicast`、`publish`），要么启动权被订阅者绑架（`share`、`cache`），要么只支持单订阅者（`unicast`），要么写读不分离（`cache`），要么已废弃（`ReplayProcessor`）。
>
> 选 `all()` 而不是 `limit(n)`，是因为 LLM 回复短、生命周期有限、要求完整回放，内存风险可控。





直接对比两个方案在需求 4、5 上的写法差异，就能看出便利性在哪。

## 需求 4：写入端和读取端分离

### 目标

```text
只有链 A 能写（tryEmitNext / emitNext）
链 B 只能读（asFlux / subscribe）
外部无法绕过 handle 直接写
```

### `ConnectableFlux + replay().connect()` 方案

```java
public class ActiveReplyHandle {
    private final ConnectableFlux<String> hot;
    private final Disposable disposable;

    public ActiveReplyHandle(Flux<String> replyChain) {
        this.hot = replyChain
                .doOnNext(this::onNext)
                .doOnError(this::onError)
                .doOnComplete(this::onComplete)
                .replay();
    }

    public Flux<String> asFlux() {
        return hot;          // ← 暴露的是 ConnectableFlux
    }

    public void start() {
        this.disposable = hot.connect();
    }

    public void emitNext(String chunk) {
        // ❌ 写不了！
        // ConnectableFlux 没有 tryEmitNext
        // 数据只能从上游 replyChain 流过来
    }
}
```

问题：

- `ConnectableFlux` **没有写入 API**。它的数据只能来自上游 `replyChain`。
- 所以 `ActiveReplyHandle` 没法提供 `emitNext(chunk)` 这样的方法。
- 那 onNext 的处理逻辑（累积 `fullResponse`、写 sink）只能挂在 `doOnNext` 里，**塞进构造函数**。
- 结果：`ActiveReplyHandle` 变成了“只读对象 + 启动开关”，写逻辑跑到外面去了。

### `Sinks.replay().all()` 方案

```java
public class ActiveReplyHandle {
    private final Sinks.Many<String> sink = Sinks.many().replay().all();
    private Disposable disposable;

    public Flux<String> asFlux() {
        return sink.asFlux();    // ← 只暴露读取端
    }

    public void emitNext(String chunk) {
        sink.tryEmitNext(chunk); // ← 写入端封装在 handle 内部
    }

    public void emitComplete() {
        sink.tryEmitComplete();
    }

    public void emitError(Throwable e) {
        sink.tryEmitError(e);
    }

    public void attach(Disposable d) {
        this.disposable = d;
    }
}
```

**便利性差异：**

| 能力 | ConnectableFlux 方案 | Sinks 方案 |
|---|---|---|
| 对外暴露读取端 | 返回 `ConnectableFlux` | 返回 `sink.asFlux()` |
| 写入 API | ❌ 没有 | ✅ `tryEmitNext` |
| 外部能否绕过 handle 写 | 不能，但 handle 自己也不能写 | 不能，只有 handle 能写 |
| 写逻辑放哪 | 只能塞在 `doOnNext` 里 | 自由：`emitNext` 方法体里 |
| 写读边界 | 模糊（都是 `hot`） | 清晰（`sink` 私有，`asFlux()` 公开） |

**关键点：**

> `Sinks.Many` 天生就是“写入端 + 读取端”双接口。  
> `ConnectableFlux` 只有读取端，写入端在上游，你没法把它封装进 handle。

`Sinks` 方案里：

```java
private final Sinks.Many<String> sink;   // 私有，只有 handle 能碰

public Flux<String> asFlux() {           // 公开，只给读取端
    return sink.asFlux();
}

public void emitNext(String chunk) {     // 公开，但语义明确是“写”
    sink.tryEmitNext(chunk);
}
```

外部拿到 `asFlux()` 只能订阅，不能写。  
handle 自己通过 `emitNext` 写，写逻辑完全在 handle 控制之下。

`ConnectableFlux` 方案做不到这一点，因为 `ConnectableFlux` 没有“往里塞数据”的接口。

## 需求 5：封装成一个可管理对象

### 目标

```text
一个对象同时持有：
  - 流本身（写入端 + 读取端）
  - Disposable（取消开关）
  - 状态（fullResponse、discard 标记等）
  - 对外接口（asFlux、emitNext、emitComplete...）
  - 可被注册表管理、被停止接口定位
```

### `ConnectableFlux` 方案

```java
public class ActiveReplyHandle {
    private final ConnectableFlux<String> hot;
    private final Disposable disposable;
    private final StringBuilder fullResponse;
    private volatile boolean discard;
    // ...
}
```

问题：

- `hot` 和 `disposable` 是**两个分开的东西**，需要手动绑定。
- `hot` 创建时就得把 `doOnNext` / `doOnError` / `doOnComplete` 挂好，**构造函数变复杂**。
- 完成/错误回调**不能后挂**，只能预先挂。
- `hot.connect()` 返回的 `Disposable` 得单独存字段。
- 如果你想在回调里访问 `fullResponse` / `discard`，得确保它们在 `doOnNext` 之前初始化好，顺序敏感。

### `Sinks` 方案

```java
public class ActiveReplyHandle {
    private final Sinks.Many<String> sink = Sinks.many().replay().all();
    private Disposable disposable;
    private final StringBuilder fullResponse = new StringBuilder();
    private volatile boolean discard;
    // ...
}
```

优势：

- `sink` 就是流本身，**既是写入端又是读取端的源头**，不用再引用上游。
- 完成/错误回调**不挂在 sink 上**，而是挂在链 A 的 `subscribe(...)` 上：

```java
replyChain.subscribe(
    handle::emitNext,           // onNext  → handle.emitNext → sink.tryEmitNext
    error -> {                  // onError → 业务逻辑 + handle.emitError
        activeReplyRegistry.release(userId, handle);
        handle.emitError(error);
    },
    () -> {                     // onComplete → 落库 + release + handle.emitComplete
        try {
            if (fullResponse.length() > 0) {
                consultationMessageService.saveAimessage(...);
            }
        } catch (Exception e) { ... }
        activeReplyRegistry.release(userId, handle);
        handle.emitComplete();
    }
);
```

- 回调**不塞进 handle 构造函数**，而是写在业务方法里，`handle` 只暴露 `emitNext` / `emitComplete` / `emitError` 三个写方法。
- `handle` 的职责非常清晰：

```text
handle = 一次生成的业务载体
  - 持有 sink（写入端私有 + 读取端公开）
  - 持有 Disposable（取消开关）
  - 提供 emitNext / emitComplete / emitError（写接口）
  - 提供 asFlux（读接口）
  - 提供 attach / dispose（生命周期管理）
  - 可被注册表管理（activeReplyRegistry）
  - 可被停止接口定位（通过 userId + handle）
```

### 对比表

| 维度 | ConnectableFlux 方案 | Sinks 方案 |
|---|---|---|
| 流对象 | `ConnectableFlux`（只有读取端） | `Sinks.Many`（写入端 + 读取端） |
| Disposable | 单独存字段，`connect()` 返回 | 单独存字段，`subscribe()` 返回 |
| 回调挂载 | 构造函数里 `doOnXxx` | 业务方法里 `subscribe(onNext, onError, onComplete)` |
| 回调时机 | 创建 hot 时必须挂好 | 启动时挂，灵活 |
| 写接口 | ❌ 没有 | ✅ `emitNext` / `emitComplete` / `emitError` |
| 读接口 | `asFlux()` 返回 `hot` | `asFlux()` 返回 `sink.asFlux()` |
| 职责边界 | 模糊（hot 既读又启动） | 清晰（sink 私有，只暴露需要的接口） |
| 构造复杂度 | 高（回调都塞构造函数） | 低（handle 只管持有 sink） |
| 业务逻辑位置 | 部分被迫塞进 handle 构造函数 | 全部在业务方法里，handle 只做载体 |

## 具体看“便利性”体现在哪

### 便利性 1：写逻辑可以随时调用，不受流创建时机限制

`Sinks` 方案：

```java
// 任何时候都能写
handle.emitNext(chunk);
handle.emitComplete();
handle.emitError(e);
```

`ConnectableFlux` 方案：

```java
// 写不了。数据只能从 replyChain 流过来。
// 如果想手动写，得额外搞一个 Sinks 或 Processor，那就绕回去了。
```

**结论：`ConnectableFlux` 没法提供写接口，写逻辑只能挂在 `doOnNext` 里，handle 无法成为“写入口”。**

### 便利性 2：回调挂载点灵活，业务逻辑不污染 handle

`Sinks` 方案：

```java
// handle 类：只关心流和状态
public class ActiveReplyHandle {
    private final Sinks.Many<String> sink = Sinks.many().replay().all();
    private Disposable disposable;
    // ...
}

// 业务方法：所有副作用逻辑都在这里
replyChain.subscribe(
    handle::emitNext,
    error -> { release(...); handle.emitError(error); },
    () -> { saveAimessage(...); release(...); handle.emitComplete(); }
);
```

`ConnectableFlux` 方案：

```java
// handle 类：不得不把业务逻辑塞进构造函数
public ActiveReplyHandle(Flux<String> replyChain) {
    this.hot = replyChain
        .doOnNext(chunk -> {
            fullResponse.append(chunk);
            // 可能还要处理 discard...
        })
        .doOnError(error -> {
            // 这里怎么 release？handle 还没构造完
            // 只能存个回调引用，绕来绕去
        })
        .doOnComplete(() -> {
            // 落库逻辑也得塞这里
        })
        .replay();
}
```

**结论：`Sinks` 方案让 handle 保持“纯载体”，业务逻辑集中在业务方法里；`ConnectableFlux` 方案迫使业务逻辑和流创建耦合在一起。**

### 便利性 3：注册表管理和停止接口定位更自然

`Sinks` 方案：

```java
// 注册表里存 handle
activeReplyRegistry.acquire(userId, handle);

// 停止接口
ActiveReplyHandle handle = activeReplyRegistry.get(userId);
handle.dispose();   // 内部调 disposable.dispose()
handle.emitComplete();
```

`ConnectableFlux` 方案：

```java
// 注册表里得同时存 handle 和 disposable，或者 handle 里再包一层
activeReplyRegistry.acquire(userId, handle);

// 停止接口
ActiveReplyHandle handle = activeReplyRegistry.get(userId);
handle.getDisposable().dispose();  // disposable 是单独字段
// 但 emitComplete 呢？ConnectableFlux 没有这个方法...
// 只能靠上游自然完成，或者别的方式终止
```

**结论：`Sinks` 方案里 handle 自带给流发终止信号的能力（`emitComplete`），停止接口可以完整控制生命周期；`ConnectableFlux` 方案里终止流只能靠取消上游订阅，语义不完整。**

## 一句话总结

> **在需求 4 上：`Sinks.Many` 天生有写入端（`tryEmitNext`）和读取端（`asFlux`），可以把写入端私有、读取端公开；`ConnectableFlux` 只有读取端，写不了，写逻辑只能挂 `doOnNext`，handle 无法成为写入口。**
>
> **在需求 5 上：`Sinks` 让 handle 成为“纯载体”——持有流、持有 Disposable、提供写接口和读接口，业务逻辑集中在业务方法里；`ConnectableFlux` 迫使业务回调塞进 handle 构造函数，职责边界模糊，注册表和停止接口管理也更别扭。**
>
> 所以选 `Sinks` 不是因为 `ConnectableFlux` 做不到功能，而是因为 `Sinks` 在“写读分离”和“业务对象封装”这两件事上，接口设计和职责划分自然得多。


不懂的点在于：**“取消上游订阅”和“让下游订阅者收到完成信号”是两件不同的事。** `ConnectableFlux` 只能做前者，做不了后者。

## 1. 先分清两个动作

### 动作 A：取消上游订阅

```java
disposable.dispose();
```

意思是：**不再从 LLM 冷流接收数据了。**

效果：

- 上游 `replyChain` 的订阅被取消；
- LLM 生成停止；
- 不会再有新的 chunk 进入 hot。

### 动作 B：让下游订阅者收到完成信号

```java
// 相当于让所有 SSE 订阅者收到 onComplete
```

意思是：**告诉所有正在看这个流的 SSE 订阅者：“流结束了，你可以正常关闭连接了。”**

效果：

- 每个订阅者的 `onComplete` 回调被触发；
- SSE handler 收到完成信号后，正常关闭 HTTP 响应；
- 浏览器知道“回复结束”，可以停止 loading 状态。

**这是两个独立的事情。** 取消上游不等于下游会收到完成信号。

## 2. `ConnectableFlux` 方案里，停止时会发生什么

假设用户点“停止生成”：

```java
ActiveReplyHandle handle = activeReplyRegistry.get(userId);
handle.getDisposable().dispose();  // 只做了动作 A
```

此时：

```text
上游 replyChain：订阅被取消，LLM 停止 ✅

hot（ConnectableFlux）：
  - 上游不再推数据
  - 但 hot 本身没有收到 onComplete
  - 因为 dispose() 只是取消订阅，不是“上游正常完成”

下游 SSE 订阅者：
  - 没有收到 onComplete
  - 也没有收到 onError
  - 只是“数据不再来了”
  - SSE 连接可能一直挂着，浏览器一直等
```

**问题：下游订阅者不知道流已经结束了。**

## 3. `Sinks` 方案里，停止时会发生什么

```java
handle.dispose();          // 动作 A：取消上游，LLM 停止
handle.emitComplete();     // 动作 B：让下游收到 onComplete
```

此时：

```text
上游 replyChain：订阅被取消，LLM 停止 ✅

sink：
  - tryEmitComplete() 被调用
  - sink 进入终止状态
  - 所有订阅者收到 onComplete

下游 SSE 订阅者：
  - 收到 onComplete ✅
  - SSE handler 正常关闭连接 ✅
  - 浏览器知道“结束了” ✅
```

**两个动作都能做，语义完整。**

## 4. 为什么 `ConnectableFlux` 做不了动作 B

`ConnectableFlux` 的终止信号**只能来自上游**：

```text
上游 onComplete → hot 广播 onComplete 给下游
上游 onError    → hot 广播 onError 给下游
```

你没有 API 能对 hot 说：“现在，立刻，给所有订阅者发一个 onComplete。”

`hot` 没有 `tryEmitComplete` 这样的方法。它只是一个“转发上游信号”的管道。

而 `dispose()` 做的是：

```text
取消对上游的订阅
  → 上游不再推数据
  → 但这不是“上游正常完成”
  → hot 不会把 dispose 转成 onComplete
  → 下游收不到完成信号
```

## 5. 用一个类比

```text
hot = 直播转播台
上游 replyChain = 现场摄像机
下游 SSE = 观众家里的电视
```

**正常结束：**

```text
摄像机关机（上游 onComplete）
  → 转播台收到“信号结束”
  → 转播台告诉所有电视：“节目结束”
  → 观众看到“节目结束”
```

**取消上游订阅（dispose）：**

```text
转播台单方面切断和摄像机的连接
  → 摄像机不再送信号
  → 但转播台没有告诉电视“节目结束”
  → 电视一直停在最后一帧，观众不知道发生了什么
```

`ConnectableFlux` 的 `dispose()` 就是“单方面切断和摄像机的连接”。  
它不会自动转化为“告诉电视节目结束”。

## 6. 那 ConnectableFlux 方案能不能补救

能，但要额外做很多事。比如：

```java
// 得自己维护一个 Sinks 来做终止信号
Sinks.Many<String> terminator = Sinks.many().replay().all();

Flux<String> output = hot.takeUntilOther(terminator.asFlux());

// 停止时
handle.getDisposable().dispose();       // 取消上游
terminator.tryEmitComplete();           // 让下游收到完成
```

或者：

```java
// 用 doOnCancel 之类的手动触发
hot.doOnCancel(() -> { /* 想办法通知下游 */ });
```

但注意：**你已经绕回来了。** 为了给 `ConnectableFlux` 补上“主动终止”的能力，你又引入了一个 `Sinks`。  
那还不如一开始就用 `Sinks` 做载体。

## 7. 所以“语义不完整”指的是

| 场景 | Sinks 方案 | ConnectableFlux 方案 |
|---|---|---|
| 停止生成 | `dispose()` + `emitComplete()` | 只能 `dispose()` |
| 下游收到完成信号 | ✅ | ❌ |
| SSE 连接正常关闭 | ✅ | ⚠️ 可能一直挂着 |
| 浏览器知道结束 | ✅ | ❌ |
| 主动发错误 | `emitError(e)` | ❌ |

**“语义不完整”= `ConnectableFlux` 只能表达“我不再接收上游数据了”，不能表达“这次生成正式结束了，请所有订阅者收尾”。**

而停止接口需要的是后者——不只是停止生成，还要让正在看的浏览器知道“结束了”。

## 8. 一句话总结

> **`dispose()` 是“切断上游”，不是“通知下游”。**
>
> **`ConnectableFlux` 只能做前者：取消对 LLM 的订阅。但它没有 API 让 hot 主动给所有 SSE 订阅者发 `onComplete`。所以停止生成后，浏览器可能收不到结束信号，SSE 连接一直挂着。**
>
> **`Sinks` 方案能同时做两件事：`dispose()` 停上游，`emitComplete()` 通知下游。这就是“语义完整”的意思。**
